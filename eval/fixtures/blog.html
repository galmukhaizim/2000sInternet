Why every build system eventually becomes a programming language

Posted by Sam · March 3, 2024 · 8 min read

There is a well-worn joke that every configuration format grows until it contains an ad-hoc, informally specified, bug-ridden implementation of half of Lisp. Build systems are the clearest example.

Make started as a tiny dependency tracker. Then it grew variables, then functions, then conditionals. CMake started as a declarative description of a build and now has a Turing-complete scripting language with its own string escaping rules.

The pressure that makes it happen

The pressure comes from the long tail. Ninety percent of projects need a handful of rules. The remaining ten percent need something nobody anticipated, and the maintainers add a hook.

Each hook is reasonable on its own. Together they form a language without a grammar.

What to do instead

Pick a real language early. Bazel's Starlark and Gradle's Kotlin are admissions of this. The build description is a program; treat it like one, with tests and linting.

None of this means your Makefile is wrong. It means you should notice the moment it stops being data.

"The best build system is the one you can explain in a paragraph." — someone, probably
